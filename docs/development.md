# Development guide

## Layout

| Project | Purpose |
| --- | --- |
| `src/AssetTracker.Core` | Domain entities, `AppDbContext` (provider-agnostic), application services, access scope, audit writer, adapter interfaces (`IClock`, `IDirectorySource`, `IMailRelay`). |
| `src/AssetTracker.Infrastructure` | SQL Server registration, EF migrations, production adapters (AD `DirectorySearcher`, SMTP relay, system clock). |
| `src/AssetTracker.Web` | ASP.NET Core Razor Pages on IIS, Windows Authentication, AD-group → app-role mapping, authorization policies. |
| `src/AssetTracker.Worker` | Windows Service hosting background jobs (AD sync, mail outbox sender, per-site overdue reminders). |
| `tests/AssetTracker.Tests` | Integration-first tests: `AppFactory` runs the real app against a real relational DB with simulated Windows principals and fake AD/relay. |

## Running locally

```bash
dotnet test                               # SQLite temp-file DB per test class
ATS_TEST_SQLSERVER="Server=...;User Id=...;Password=...;TrustServerCertificate=True" dotnet test   # real SQL Server
```

The production app requires `ConnectionStrings:AssetTracker`, `Roles:*GroupSids` and `DataProtection:KeyPath` in its config file, and `Clock:TimeZoneId` (plus the AD and mail settings) on Admin → Settings. **No production values are defaulted**: they come from Stage 0 (see issue #2).

## Conventions

- **Authorization lives in services and queries, not just pages.** Every read path goes through `AccessScope` (`VisibleAssetsAsync`, `VisiblePoolsAsync`, `VisibleLoansAsync`, `EnsureCanReadSiteAsync`). Every mutation calls `AccessScope.EnsureIt()` (or `EnsureAdmin()` for settings/grants). Page policies (`Policies.ItOnly` / `InventoryRead` / `AdminOnly`) are a second layer.
- **Audit in the same transaction.** Call `AuditWriter.Record(...)` before `SaveChangesAsync()`; never write audit in a separate save.
- **Errors.** Throw `DomainException` (400), `ConflictException` (409) or `AccessDeniedException` (rendered as 404). Pages get this mapping via `DomainExceptionFilter`.
- **Concurrency.** Never read-modify-write a pool balance. Use a conditional atomic update, e.g. `ExecuteUpdateAsync(... WHERE Available >= @q)`, and check the affected row count. A tagged asset's single open loan is enforced by the `UX_Loans_OpenAsset` unique index; translate its `DbUpdateException` into a `ConflictException`.
- **Time (WP4.2).** Store and compare instants as UTC `DateTimeOffset` via `IClock.UtcNow` (return/correction "not in the future" checks stay instant-based). `IClock` deliberately has no "local today": calendar days are per site. Use `SiteCalendar` (Core/Time): `TodayForAsync(siteId)`, `TodayForAsync(loan)` (tagged loan → the asset's **current** site, pool loan → the pool's site), `LocalTimeForAsync(siteId)`, `AllSitesAsync()` and `OverduePredicateAsync()` for queries. A site's zone is `Site.TimeZoneId` (IANA or Windows id), else the default `Clock:TimeZoneId` (`ClockOptions`, read via `IOptionsMonitor`); neither set ⇒ `InvalidOperationException`. `SiteCalendar.DefaultToday` is only for things that belong to no site (export file names). Due dates are `DateOnly` in the loan's site calendar and must be ≥ that site's today at checkout.
- **Overdue rule (D4).** `OverduePolicy` is the only definition: overdue when `siteToday >= DueDate` (from the start of the due date); `DaysOverdue = siteToday − DueDate` (0 on the due date, shown as "due today"). Reports, the loans list filter, the reports summary and reminders all use it through `SiteCalendar`. Tests: the default zone is UTC (`AppFactory`), `FakeClock.UtcToday` is every default-zone site's today; give a test site a `TimeZoneId` to test another zone.
- **Migrations.** Feature branches change the model freely; migrations are regenerated by the integrator (`dotnet ef migrations add <Name> -p src/AssetTracker.Infrastructure -s src/AssetTracker.Infrastructure -o Data/Migrations`). CI fails if the model and migrations differ.
- **Tests.** Prefer `AppFactory` integration tests (HTTP via `CreateClientAs(TestUser.X)` or services via `RunAsAsync(TestUser.X, sp => ...)`). Use fictional fixture data from `Seed`. Use unique site keys/tags per test, because each test class shares one database.
- **Service registration.** Add scoped services in `CoreServiceCollectionExtensions.AddAssetTrackerCore` and adapters in `InfrastructureServiceCollectionExtensions`.
- **Append-only ledgers.** `AppDbContext.SaveChanges*` throws `InvalidOperationException` if an `AuditEvent`, `LoanEvent` or `StockEvent` is modified or deleted through the change tracker. Never use `ExecuteUpdate`/`ExecuteDelete` on those sets (they bypass the guard). The one permitted update is linking a transfer pair: `StockEvent.CounterpartEventId` may be set once, from null.
- **Audit visibility: IT only (sponsor decision D2, `docs/decisions.md`).** `/Audit` (policy `ItOnly`) and `AuditQueryService` (`EnsureIt`) are read-only; there is no edit/delete path. Admins cannot read or alter audit by the admin role alone.

## Database-backed settings (WP4.1)

- **Where values come from.** `AppSettings` rows whose key is a configuration path in the `ActiveDirectory`, `DirectorySync`, `Mail`, `Notifications` or `Clock` section (`SettingCatalog.IsConfigKey`) are overlaid on the appsettings files by `DatabaseSettingsConfigurationProvider` (Infrastructure/Configuration), the **last** configuration source, so the database wins. Other keys (`Mail.ItMailbox`, `Worker.Heartbeat`, `Worker.Version`, and anything like `Roles:*` or `ConnectionStrings:*`) are never exposed as configuration. Options classes bind unchanged (`services.Configure<T>(config.GetSection(...))`).
- **How the provider reaches the database.** The provider is built with the configuration, before DI exists, so it never opens a connection itself. `DatabaseSettingsReloader` (singleton `ISettingsReloader`) reads the rows through a scoped `AppDbContext` — whatever the host registered: SQL Server in production, the test database under `AppFactory` — and calls `provider.Apply(rows)`, which swaps the data and fires the reload token only when something changed. Program.cs (web and worker) calls `LoadDatabaseSettingsAsync()` right after `Build()` (it also moves the source to the end if a later source was added, e.g. by `WebApplicationFactory`); `DatabaseSettingsRefreshService` reloads every `Settings:ReloadInterval` (30 s); `SettingsService` reloads after each save. A database error (unreachable, table not migrated yet) is logged once and the previous values stay; it never throws.
- **Consumers must read live values.** Singletons inject `IOptionsMonitor<T>` and read `CurrentValue` per use (`SmtpMailRelay`, `ActiveDirectorySource`, `DirectorySyncJob`, `OutboxSenderJob`, ...). For these five sections `IOptions<T>` is registered transient and resolves to the current value, so a scoped service that injects `IOptions<T>` sees changes on its next scope; a singleton that captures `IOptions<T>` would not.
- **Editing.** `SettingsService` (Core/Settings, admin only) validates a whole section (`SettingCatalog` holds keys, labels, kinds, defaults and validation; defaults must equal the options classes, pinned by `SettingsConfigurationTests.Catalog_defaults_match_the_option_class_defaults`), writes rows, audits each changed key as `setting.update` (`{before, after}`), then reloads. Empty value = remove the override. To make a new setting editable, add it to `SettingCatalog` (page and validation follow).
- **Secrets.** `Mail:Password` is stored as Data Protection ciphertext (`ISecretProtector`, purpose `AssetTracker.Settings.Secret.v1`) and exposed to configuration only as `Mail:PasswordProtected`; `SmtpMailRelay` decrypts at send time. It is write-only on the page and audited as `{secret: true, change: set|cleared}`. Web and worker share the key ring: `AddAssetTrackerDataProtection` sets the application name `AssetTracker` and persists keys to `DataProtection:KeyPath` (machine DPAPI on Windows); Testing uses an ephemeral key ring.
- **Test buttons.** *Test directory query* calls `DirectorySyncService.PreviewAsync` (same validation and safety checks as a run, no writes; audited `directory.preview`); *Send test email* calls `IMailRelay` directly (audited `mail.test`).

## Directory sync (WP1.4)

`DirectorySyncService` (Core) runs a full sync from `IDirectorySource`; the worker's `DirectorySyncJob` schedules it and admins can rerun it from `/Admin/Sync`. IT can view `/Admin/Sync` read-only (policy `ItOrAdmin`, D7); the rerun POST is admin-only (403 otherwise). A `Failed` or `Rejected` run stages one `SystemAlert` mail to the IT mailbox (`sync-alert:{runId}`, `NotificationService.QueueSystemAlertAsync`) in the same save as the run (D6). The production adapter `ActiveDirectorySource` (Infrastructure, Windows only) uses a paged `DirectorySearcher` (subtree, `PageSize` 500).

These are edited on Admin → Settings (see above).

| Setting | Default | Notes |
| --- | --- | --- |
| `DirectorySync:Interval` | none | Worker schedule (e.g. `01:00:00`), re-read at least every minute. Unset ⇒ the worker logs an error and does not sync until it is set; IT sees the stale warning. |
| `DirectorySync:MaxDropFraction` | `0.2` | **Safety check, on by default.** A run that would deactivate more than 20% of currently active people (absent or disabled) is `Rejected` and not applied. |
| `DirectorySync:MinimumExpectedCount` | `0` (off) | Absolute floor on valid entries; set from the client's directory size in Stage 0. A run with zero valid entries is always rejected. |
| `DirectorySync:StaleAfter` | `1.00:00:00` | Placeholder until the sync frequency is agreed; drives the IT stale banner and `GetStatusAsync()`. |
| `ActiveDirectory:SearchRoot` | none | LDAP path of the in-scope OU. Required. |
| `ActiveDirectory:SiteAttribute` | none | Attribute holding the designated site. Required. |
| `ActiveDirectory:Filter`, `IdAttribute`, `PageSize`, `*Attribute` | standard AD names | `objectGUID` id, `sAMAccountName`, `displayName`, `title`, `mail`, `objectSid`, `userAccountControl` (bit 0x2 = disabled; missing ⇒ treated as disabled). |

Rules: people are keyed on the directory id (rename updates the same row) and never deleted; absent or disabled ⇒ `IsActive = false`. Entries without id/username, or sharing an id or SID with another entry, are quarantined (skipped and reported; an existing person with that id is left untouched). A site value that matches no `Site.DirectoryValue` (case-insensitive) is **not** quarantined: the person is synced with no site and an `unmapped-site` issue is recorded. A failed fetch (`Failed`) or a safety-check rejection (`Rejected`) leaves the previous snapshot unchanged. Each run writes one `directory.sync` audit event.

## Operations, security headers and privacy (WP3.2)

- **Health:** `/health` (liveness, no checks) and `/health/ready` (database, directory sync, mail outbox, worker heartbeat; `Web/Health/ReadinessChecks.cs`). Both anonymous; the JSON writer emits only fixed descriptions. Thresholds: `Ops:*` (`OpsOptions`). See `docs/runbook.md` §8.
- **Worker heartbeat:** `WorkerHeartbeatJob` upserts `AppSetting` rows `Worker.Heartbeat` / `Worker.Version` (`UpdatedBy = system:worker`) every `Worker:HeartbeatInterval`; `OpsStatusService` reads them. The IT dashboard is `/Ops`.
- **Security headers:** `Web/Security/SecurityHeaders.cs` sets CSP (`script-src 'self'; style-src 'self'`, no inline), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`, and `Cache-Control: no-store` on every non-static response. **Do not add inline `<script>`, `<style>`, `style=""` or `on*=` handlers**; use `wwwroot/js/site.js` (e.g. `data-confirm="..."` on a form) and `site.css`.
- **Privacy:** `PrivacyService.AnonymizePersonAsync` (admin, audited `privacy.anonymize`) and `Person.IsAnonymized`, which `DirectorySyncService` never updates. New code that stores holder personal data in a *mutable* table must be added to the anonymization scrub; never put names/emails into append-only ledgers. See `docs/privacy-and-retention.md`.
